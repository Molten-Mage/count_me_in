First attempt used a new `Molten-Mage/Molten-Mage.github.io` repo (still exists, now unused/dead) — abandoned because GitHub Pages can't serve a custom `Content-Type` for an extension-less file, and `apple-app-site-association` (no extension, by Apple's own requirement) kept coming back as `application/octet-stream` instead of the `application/json` iOS's verification expects. Real device testing confirmed iOS silently failed Universal Links verification because of it — link taps briefly flashed the app then fell back to Safari, with no error surfaced anywhere. Cloudflare Pages solves it with a `_headers` file forcing the right Content-Type. Deployed via `wrangler` (Cloudflare's CLI, `npm install -g wrangler` + `wrangler login` + `wrangler pages deploy`) from the `cf-pages/` folder at the repo root (redeploy with `wrangler pages deploy cf-pages --project-name=count-me-in-links` after editing any of its files). `404.html` links to the [App Store listing](https://apps.apple.com/us/app/count-me-in-group-challenges/id6801997166) via a manual "Get the app" button plus an `apple-itunes-app` Smart App Banner (which offers a native "Open" action when the app's already installed). A JS auto-redirect (`window.location.replace`) was tried and removed - landing on this page doesn't reliably mean the app is missing, since Universal Links can flash the app open then still fall back to Safari (an OS-level race, see below), and the forced redirect fought the Smart Banner's correct "Open" behavior in exactly that case. `ios/Runner/Runner.entitlements` has the Associated Domains entitlement (`applinks:count-me-in-links.pages.dev`); `AndroidManifest.xml` has an `autoVerify="true"` intent filter for the same host/path, alongside the `countmein://` scheme kept as a fallback.
